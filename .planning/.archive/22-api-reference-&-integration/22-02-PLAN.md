**2. Error Hierarchy**
Austria MCP error types:
- **ToolError** - User-facing errors (FastMCP displays to user)
  - When: Invalid input, resource not found, expected failures
  - Example: "Dataset 'xyz' not found. Check ID spelling."
- **PiveauApiError** - Internal API errors (logged, converted to ToolError)
  - When: Unexpected API responses, malformed data
- **PiveauNotFoundError** - Specific 404 cases
- **PiveauAuthError** - Authentication failures (401/403)
- **Transient errors** - Network, timeout (retry via RetryMiddleware)

Code example showing hierarchy from mcp/app/client.py

**3. ToolError Best Practices**
From established patterns (STATE.md decision 79, 83):

**Always use ToolError for tool-level errors:**
```python
from fastmcp.exceptions import ToolError

# Good - actionable, specific
raise ToolError(
    "Dataset 'population-2023' not found. "
    "Check ID spelling or use search_datasets to find available datasets."
)

# Bad - generic, unhelpful
raise Exception("Not found")
```

**Error message guidelines:**
- Be specific: Include IDs, values, context
- Be actionable: Tell user what to check/try
- Be friendly: Avoid stack traces, technical jargon

**Code examples from mcp/app/client.py:**
- Connection errors with diagnostic guidance
- HTTP status error handling (4xx vs 5xx)
- Validation errors with parameter constraints

**4. Middleware Error Flow**
How errors propagate through middleware stack:

```
Tool raises ToolError
  ↓
AuditMiddleware logs error (timing, parameters)
  ↓
RetryMiddleware checks if retryable (NO for ToolError)
  ↓
ErrorHandlingMiddleware formats for MCP protocol
  ↓
StructuredLoggingMiddleware logs final outcome
  ↓
Client receives formatted error
```

**When RetryMiddleware retries:**
- Connection errors (httpx.ConnectError, httpx.TimeoutException)
- Server errors (500, 502, 503, 504)
- NOT retried: 4xx errors, ToolError, validation errors

Code example from mcp/app/middleware.py showing RetryMiddleware logic

**5. Error Handling Patterns**

**Pattern 1: Transient vs Permanent Errors**
```python
try:
    response = await client.request(...)
except httpx.ConnectError as e:
    # Transient - RetryMiddleware will retry
    raise ToolError(
        f"Piveau API unavailable: {e}. "
        "Check network connection and API status."
    ) from e
except httpx.HTTPStatusError as e:
    if e.response.status_code >= 500:
        # Transient server error
        raise ToolError(f"API error {e.response.status_code}") from e
    elif e.response.status_code == 404:
        # Permanent error
        raise ToolError(f"Dataset not found") from e
```

**Pattern 2: Optional Features Degrade Gracefully**
From STATE.md decision 83:
```python
try:
    semantic_expansion = await expander.expand(query)
    themes = semantic_expansion.themes
except Exception as e:
    logger.warning(f"Semantic expansion failed: {e}")
    themes = []  # Degrade to basic search
```

**Pattern 3: Core Features Fail Fast**
```python
if not dataset_id:
    raise ToolError("dataset_id is required")

if not is_valid_id(dataset_id):
    raise ToolError(
        f"Invalid dataset_id: '{dataset_id}'. "
        "IDs must be 1-200 characters."
    )
```

async def get_dataset(ctx: Context, dataset_id: str):

**4. Mock Context Pattern**
From tests/conftest.py:

**Creating mock Context:**
```python
from unittest.mock import AsyncMock, MagicMock
from fastmcp import Context

def create_mock_context(
    settings: Settings | None = None,
    client: AsyncMock | None = None,
) -> MagicMock:
    """Create mock Context with app state."""
    if settings is None:
        settings = Settings(piveau_api_base="https://test.api")
    if client is None:
        client = AsyncMock(spec=PiveauClient)

    app_state = AppState(
        settings=settings,
        piveau_client=client
    )

    ctx = MagicMock(spec=Context)
    ctx.request_context = MagicMock()
    ctx.request_context.lifespan_context = app_state
    ctx.report_progress = AsyncMock()
    ctx.request_id = "test-request-123"

    return ctx
```

**Why this pattern:**
- Context provides app state to tools
- Mock allows controlling PiveauClient responses
- AsyncMock for async methods (report_progress)

**5. Testing Tools (Unit Tests)**

async def test_search_datasets_success():
    # Arrange: Mock client response
    mock_client = AsyncMock(spec=PiveauClient)

        "results": [{"id": "ds-1", "title": "Dataset 1"}],
        "count": 1,
        "facets": {}
    }

    ctx = create_mock_context(client=mock_client)

    # Act: Call tool

    # Assert: Verify result
    assert result["count"] == 1
    assert len(result["results"]) == 1

**9. Testing Best Practices**

**DO:**
- Mock external dependencies (APIs, databases)
- Test both success and failure paths
- Use descriptive test names (test_search_returns_empty_when_no_results)
- Test error messages (use pytest.raises with match=)
- Use fixtures for common setup
- Run tests frequently during development

**DON'T:**
- Use subprocess for testing (slow, flaky)
- Make real network calls (non-deterministic)
- Test FastMCP framework itself (trust the framework)
- Skip error cases (most bugs are in error handling)
- Use sleep() for timing (use mocks, not real delays)

From 22-RESEARCH.md Common Pitfalls:
- Don't spawn subprocess (use in-memory Client)
- Don't skip Context mocking (tools need app state)
- Don't ignore async (use pytest-asyncio)

**11. Debugging Test Failures**

Common failures and solutions:
- **AsyncMock not awaited**: Use `AsyncMock()`, not `MagicMock()`
- **Context missing app state**: Use `create_mock_context()` fixture
- **Tests hang**: Async test missing `@pytest.mark.asyncio`
- **Flaky tests**: Check for real network calls, time dependencies

pytest -v --tb=short      # Short traceback
pytest -x                 # Stop on first failure
