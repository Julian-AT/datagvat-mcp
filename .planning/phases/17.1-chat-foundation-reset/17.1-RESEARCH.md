# Phase 17.1: Chat Foundation Reset - Research

**Researched:** 2026-02-01
**Domain:** AI chat architecture, message persistence, streaming protocols
**Confidence:** HIGH

## Summary

The vercel/ai-chatbot repository provides a battle-tested foundation for AI chat applications using Vercel AI SDK 6.x. After analyzing their codebase (commit b6be233 shows we're at a similar point), the key insight is: **they use a parts-based message architecture that enables clean separation of content types, proper streaming, and efficient persistence**.

Our custom implementation hit fundamental issues (context window explosion, WebSocket payload errors, visualization persistence failures) because we attempted to handle complex content (base64 visualizations) through the streaming pipeline instead of using the proven pattern: **upload to blob storage first, reference by URL in messages**.

The standard approach is:
1. Messages stored with `parts` array (text, tool-call, tool-result, file)
2. Files/visualizations uploaded to Vercel Blob immediately, referenced by URL
3. Stream carries only metadata and text, not binary data
4. Database schema uses JSONB for flexible parts storage
5. No custom `experimental_transform` needed - use data stream annotations properly

**Primary recommendation:** Adopt their DB schema (chat + message tables with parts/attachments JSONB), file upload pattern (immediate blob storage), and message rendering approach (map through parts array). Keep our MCP tools and E2B integration exactly as-is - they're working perfectly.

### Pattern 1: Parts-Based Message Architecture
**What:** Messages stored as arrays of typed parts instead of single content field
**When to use:** All AI chat applications with multimodal content (text, images, tool calls)
**Example:**
```typescript
// Source: vercel/ai-chatbot lib/db/schema.ts
export const message = pgTable("message", {
  id: uuid("id").primaryKey().defaultRandom(),
  chatId: uuid("chat_id").references(() => chat.id),
  role: varchar("role", { length: 20 }).notNull(),
  parts: json("parts").$type<Array<
    | { type: "text"; text: string }
    | { type: "tool-call"; toolCallId: string; toolName: string; args: any }
    | { type: "tool-result"; toolCallId: string; toolName: string; result: any }
    | { type: "file"; url: string; name: string; mediaType: string }
  >>().notNull(),
  attachments: json("attachments").$type<Attachment[]>().notNull(),
  createdAt: timestamp("created_at").notNull(),
});
```

### Pattern 2: Upload-First File Handling
**What:** Files uploaded to blob storage BEFORE sending message, message references URL
**When to use:** Any content larger than 10KB or binary data (images, visualizations)
**Example:**
```typescript
// Source: vercel/ai-chatbot components/multimodal-input.tsx
const submitForm = useCallback(() => {
  sendMessage({
    role: "user",
    parts: [
      ...attachments.map((attachment) => ({
        type: "file" as const,
        url: attachment.url,  // Already uploaded, just reference
        name: attachment.name,
        mediaType: attachment.contentType,
      })),
      { type: "text", text: input },
    ],
  });
}, [input, attachments, sendMessage]);

// Upload happens earlier, before submission:
const uploadFile = useCallback(async (file: File) => {
  const formData = new FormData();
  formData.append("file", file);
  const response = await fetch("/api/files/upload", { method: "POST", body: formData });
  const { url, pathname, contentType } = await response.json();
  return { url, name: pathname, contentType };
}, []);
```

### Pattern 3: Immediate Message Persistence
**What:** Save user message BEFORE streaming, save assistant response in onFinish
**When to use:** Always - ensures messages never lost even if stream fails
**Example:**
```typescript
// Source: vercel/ai-chatbot app/(chat)/api/chat/route.ts
export async function POST(request: Request) {
  // ... validation, auth ...

  // Create or get chat
  let chat = await getChatById({ id: chatId });
  if (!chat) {
    await saveChat({ id: chatId, userId, title: "New chat", visibility: "private" });
  }

  // Save user message BEFORE streaming starts
  const userMessage = {
    id: generateId(),
    chatId,
    role: "user",
    parts: uiMessages[0].parts,
    attachments: [],
    createdAt: new Date()
  };
  await saveMessages({ messages: [userMessage] });

  // Now stream response
  const stream = createUIMessageStream({
    execute: async ({ writer }) => {
      const result = streamText({ /* ... */ });
      writer.merge(result.toUIMessageStream());
    },
    onFinish: async ({ messages }) => {
      // Save assistant response after streaming completes
      await saveMessages({ messages: messages.slice(-1) });
    },
  });

  return createUIMessageStreamResponse({ stream });
}
```

### Pattern 5: Message Part Rendering
**What:** Map through parts array, render different component per type
**When to use:** Displaying messages with mixed content (text + images + tool results)
**Example:**
```typescript
// Source: vercel/ai-chatbot components/message.tsx (adapted)
export function Message({ message }: { message: ChatMessage }) {
  const attachments = message.parts.filter(p => p.type === "file");

  return (
    <div data-role={message.role}>
      {/* Show attachments first */}
      {attachments.map(att => (
        <PreviewAttachment key={att.url} attachment={att} />
      ))}

      {/* Render each part */}
      {message.parts.map((part, idx) => {
        if (part.type === "text") {
          return <MessageContent key={idx}>{part.text}</MessageContent>;
        }
        if (part.type === "tool-call") {
          return <ToolCallDisplay key={idx} toolCall={part} />;
        }
        if (part.type === "tool-result") {
          return <ToolResultDisplay key={idx} result={part} />;
        }
        return null;
      })}
    </div>
  );
}
```

### Anti-Patterns to Avoid
- **Using experimental_transform for content manipulation:** The transform stream is for monitoring/debugging only. Don't use it to modify chunks or handle business logic. Use data stream annotations instead.
- **Passing base64 data through tool results:** Context window explosion and WebSocket payload errors. Always upload binary data to blob storage first, pass URLs.
- **Custom visualization caching in memory:** Our approach with `visualizationCache` Map was a workaround. Proper pattern: upload in tool execute function, return URL immediately.
- **Saving messages only in onFinish:** If stream fails, messages lost. Save user message before streaming starts.
- **Single content field in DB schema:** Can't represent multimodal messages. Use parts array from day one.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| File upload handling | Custom FormData parser, validation | Vercel Blob `put()` + Zod validation | Handles multipart parsing, size limits, MIME validation, CDN distribution automatically |
| Message streaming | Custom SSE implementation | `createUIMessageStream` + `createUIMessageStreamResponse` | Handles backpressure, error propagation, message merging, client reconnection |
| Message persistence | Raw SQL with custom types | Drizzle ORM with typed schema | Type safety, migrations, relationship handling, query builder |
| Stream reconnection | Custom Redis checkpoint logic | `resumable-stream` library | Production-tested resumption, handles edge cases (multiple tabs, network switches) |
| UI message state | Custom reducer for message updates | `useChat` hook from @ai-sdk/react | Handles optimistic updates, error rollback, tool approval flow, attachment state |
| Blob storage URLs | Direct S3 integration | @vercel/blob | Zero-config CDN, automatic cleanup, usage tracking, built-in security |

**Key insight:** The AI SDK provides createUIMessageStream specifically to avoid building custom streaming infrastructure. Our experimental_transform usage was fighting the framework - the right way is to use the SDK's built-in data stream annotations.

## Common Pitfalls

### Pitfall 1: Context Window Explosion from Tool Results
**What goes wrong:** Including base64-encoded images (50-200KB) in tool results causes:
- 236K+ token messages (our exact issue at commit b6be233)
- Model context exhaustion after 2-3 visualizations
- Slow responses due to re-processing large context

**Why it happens:** E2B returns visualizations with base64 data. Naively returning this in tool result sends it to LLM AND client AND database.

**How to avoid:**
1. Upload binary data to blob storage INSIDE the tool execute function
2. Return only metadata in tool result: `{ visualizationUrl: "https://..." }`
3. Never include base64 in tool results, even temporarily

**Warning signs:**
- Token counts above 50K for single messages
- WebSocket payload errors in browser console
- "Context length exceeded" errors from model

**Code example (correct pattern):**
```typescript
tools['execute-python'] = tool({
  execute: async ({ code }) => {
    const result = await sandbox.runCode(code);

    if (result.visualizations?.length > 0) {
      // Upload IMMEDIATELY, inside tool execution
      const uploadPromises = result.visualizations.map(async (viz, i) => {
        const url = await uploadImageFromBase64(
          viz.png,
          `viz-${Date.now()}-${i}.png`,
          conversationId
        );
        return { format: 'png', url };
      });

      const uploadedViz = await Promise.all(uploadPromises);

      // Return URLs only, no base64
      return {
        success: true,
        text: result.text,
        visualizations: uploadedViz  // [{ format: 'png', url: 'https://...' }]
      };
    }

    return result;
  }
});
```

### Pitfall 2: Streaming Binary Data
**What goes wrong:** WebSocket payload errors, failed streams, corrupted data
**Why it happens:** SSE/WebSocket designed for text, not binary. Base64 encoding doesn't help - data is still too large for efficient streaming.
**How to avoid:** Never stream binary data. Upload to storage, stream the URL.
**Warning signs:** Browser console errors about payload size, stream connection drops, visual artifacts

### Pitfall 3: Missing Message Persistence Before Stream
**What goes wrong:** User sends message, stream fails, message disappears from history
**Why it happens:** Saving messages only in onFinish callback means stream failure = data loss
**How to avoid:**
1. Save user message BEFORE calling streamText
2. Create conversation record if new chat
3. Save assistant response in onFinish (can retry if fails)

**Code pattern:**
```typescript
// BEFORE streaming
const conversation = await getOrCreateConversation(conversationId, userId);
await saveMessages({ messages: [userMessage] });

// NOW safe to stream
const stream = createUIMessageStream({ /* ... */ });
```

### Pitfall 4: Complex Part Types in Database
**What goes wrong:** TypeScript types out of sync with DB, query errors, data loss
**Why it happens:** JSONB column needs explicit type casting, easy to drift from TS types

**How to avoid:**
1. Define MessagePart type union in schema file
2. Use Drizzle's `.$type<MessagePart[]>()` for type safety
3. Validate parts with Zod before insert
4. Create indexes on JSONB if querying by part type: `index().using("gin", table.parts)`

**Example (correct):**
```typescript
// In schema.ts
export type MessagePart =
  | { type: "text"; text: string }
  | { type: "tool-call"; toolCallId: string; toolName: string; args: any }
  | { type: "tool-result"; toolCallId: string; toolName: string; result: any }
  | { type: "file"; url: string; name: string; mediaType: string }
  | { type: "visualization"; format: string; url: string; metadata?: any };

export const messages = pgTable("messages", {
  parts: jsonb("parts").$type<MessagePart[]>().notNull(),
  // ...
}, (table) => [
  index("message_parts_gin").using("gin", table.parts),
]);
```

### Pitfall 5: Incorrect Data Stream Annotation Usage
**What goes wrong:** Custom data not reaching client, handler not triggered, UI out of sync
**Why it happens:** Must use specific pattern: `type: "data-*"` prefix, write via writer.write(), consume in DataStreamHandler

**How to avoid:**
```typescript
// Server - CORRECT
writer.write({
  type: "data-visualization-ready",  // Must start with "data-"
  data: { vizId: "123", url: "https://..." }
});

// Client - CORRECT
useEffect(() => {
  for (const delta of dataStream) {
    if (delta.type === "data-visualization-ready") {
      // Handle custom event
      setVisualization(delta.data);
    }
  }
}, [dataStream]);
```

### File Upload API Route
```typescript
// Source: vercel/ai-chatbot app/(chat)/api/files/upload/route.ts
import { put } from "@vercel/blob";
import { z } from "zod";

const FileSchema = z.object({
  file: z
    .instanceof(Blob)
    .refine((file) => file.size <= 5 * 1024 * 1024, {
      message: "File size should be less than 5MB",
    })
    .refine((file) => ["image/jpeg", "image/png"].includes(file.type), {
      message: "File type should be JPEG or PNG",
    }),
});

export async function POST(request: Request) {
  const session = await auth();
  if (!session) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });

  const formData = await request.formData();
  const file = formData.get("file") as Blob;
  const validatedFile = FileSchema.safeParse({ file });

  if (!validatedFile.success) {
    return NextResponse.json({ error: validatedFile.error.errors[0].message }, { status: 400 });
  }

  const filename = (formData.get("file") as File).name;
  const fileBuffer = await file.arrayBuffer();

  const data = await put(`${filename}`, fileBuffer, { access: "public" });
  return NextResponse.json(data);  // { url, pathname, contentType }
}
```

### Chat Streaming Endpoint
```typescript
// Source: vercel/ai-chatbot app/(chat)/api/chat/route.ts (simplified)
export async function POST(request: Request) {
  const { messages, chatId, selectedChatModel } = await request.json();
  const session = await auth();

  // Ensure chat exists
  let chat = await getChatById({ id: chatId });
  if (!chat) {
    await saveChat({ id: chatId, userId: session.user.id, title: "New chat" });
  }

  // Save user message BEFORE streaming
  const userMessage = {
    id: generateId(),
    chatId,
    role: "user",
    parts: messages[messages.length - 1].parts,
    attachments: [],
    createdAt: new Date(),
  };
  await saveMessages({ messages: [userMessage] });

  // Stream response
  const stream = createUIMessageStream({
    execute: async ({ writer }) => {
      const result = streamText({
        model: getLanguageModel(selectedChatModel),
        messages: await convertToModelMessages(messages),
        tools: await getAvailableTools(),
      });

      writer.merge(result.toUIMessageStream());
    },
    onFinish: async ({ messages: finishedMessages }) => {
      // Save assistant response after stream completes
      const assistantMessage = finishedMessages[finishedMessages.length - 1];
      await saveMessages({ messages: [assistantMessage] });
    },
  });

  return createUIMessageStreamResponse({ stream });
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Single `content` field | `parts` array with typed unions | AI SDK v6.0 (2024) | Enables multimodal messages, cleaner rendering |
| Client-side file encoding | Server-side upload-first | Vercel Blob release | Reduces client bundle, faster uploads, CDN benefits |
| Custom SSE parsing | `createUIMessageStream` | AI SDK v6.0 | Simplified server code, built-in error handling |
| Message v1 schema | Message v2 with parts/attachments | ai-chatbot v2 (2024) | Migration guide available, better type safety |
| Custom transform for data | Data stream annotations | AI SDK v6.x | Documented pattern, no experimental APIs |

**Deprecated/outdated:**
- **Message table without parts column:** Old schema used single `content` text field. Migration required to support multimodal.
- **experimental_transform for content manipulation:** Was experimental workaround, now replaced by proper data stream annotations
- **Inline base64 in messages:** Never worked well at scale, always caused issues. Upload-first is the only viable pattern.
- **Vote table v1:** Replaced with v2 that uses composite primary key (chatId + messageId)

## Open Questions

Things that couldn't be fully resolved:

1. **Migration strategy for existing conversations**
   - What we know: We have ~10-20 test conversations in current schema (conversations + messages with custom MessagePart types)
   - What's unclear: Whether to migrate data or start fresh, impact on user experience
   - Recommendation: Check conversation count. If < 50, consider fresh start. If > 50, write migration script to convert parts array format.

2. **Custom visualization part type**
   - What we know: Their schema doesn't have `type: "visualization"`, uses `type: "file"` for all attachments
   - What's unclear: Best practice for distinguishing visualization images from user uploads
   - Recommendation: Add custom part type to their schema (they use CustomUIDataTypes for extensibility). Store as `{ type: "visualization", format: "png", url: string, metadata: any }`.

3. **E2B sandbox lifecycle with new architecture**
   - What we know: Our E2B client works perfectly, creates/destroys sandboxes correctly
   - What's unclear: Whether to keep current visualization caching approach or upload immediately in tool execute
   - Recommendation: Upload immediately in tool execute function (inside try/finally before sandbox.kill()). Eliminates cache complexity, reduces failure modes.

4. **Real-time visualization streaming**
   - What we know: Users want to see visualizations as they're generated, not after full completion
   - What's unclear: How to stream visualization metadata while upload is in progress
   - Recommendation: Use data stream annotation `data-visualization-progress` with upload promise, render placeholder until resolved.
