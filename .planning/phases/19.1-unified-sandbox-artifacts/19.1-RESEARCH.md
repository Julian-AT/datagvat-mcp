# Phase 19.1: Unified Sandbox Artifacts - Research

**Researched:** 2026-02-03
**Domain:** Interactive code sandbox artifacts with integrated execution, approval, and output display
**Confidence:** MEDIUM-HIGH

## Summary

This phase replaces two separate systems (static `createDocument` artifacts + `execute-python` tool) with a unified "sandbox artifact" paradigm. The research reveals this is architecturally similar to existing artifact patterns but with additional complexity: tool-triggered artifact creation, inline approval workflows, persistent execution state, and real-time output streaming.

**Key architectural findings:**
- AI SDK's tool approval workflow requires two model calls (request → approval → execution), necessitating careful state management
- CodeMirror 6 is already integrated in the project and suitable for the code editor component
- SWR-based state management pattern is established for artifacts, extensible to multiple simultaneous sandboxes
- E2B Code Interpreter returns structured results (text, logs, visualizations) that map cleanly to tabbed output display
- Database schema must store sandbox state (code, outputs, execution history) separately from message parts to support page refresh restoration

**Primary recommendation:** Extend existing artifact architecture (UIArtifact + data-stream-handler pattern) with new 'sandbox' kind, implement openSandbox tool following createDocument pattern, and store sandbox state in new database table with foreign key to message for persistence.

### Pattern 1: Tool-Triggered Artifact Creation
**What:** AI tool creates artifact via dataStream writes during execute phase
**When to use:** Any tool that needs to display interactive UI (sandbox, document, visualization)
**Example:**
```typescript
// Source: docs/lib/ai/tools/create-document.ts (lines 28-94)
export const openSandbox = ({ session, dataStream }: OpenSandboxProps) =>
  tool({
    description: "Open an interactive Python sandbox for code execution",
    needsApproval: false, // Approval happens at execution time, not sandbox creation
    inputSchema: z.object({
      title: z.string(),
      initialCode: z.string().optional(),
    }),
    execute: async ({ title, initialCode }) => {
      const sandboxId = generateUUID();

      // Stream artifact metadata to client
      dataStream.write({ type: "data-kind", data: "sandbox", transient: true });
      dataStream.write({ type: "data-id", data: sandboxId, transient: true });
      dataStream.write({ type: "data-title", data: title, transient: true });
      dataStream.write({ type: "data-clear", data: null, transient: true });

      // Initialize sandbox state
      if (initialCode) {
        dataStream.write({ type: "data-code", data: initialCode, transient: true });
      }

      dataStream.write({ type: "data-finish", data: null, transient: true });

      return {
        sandboxId,
        title,
        message: "Sandbox opened - user can edit code and run",
      };
    },
  });
```

### Pattern 2: Inline Approval Workflow
**What:** Approval UI embedded in sandbox artifact, not separate modal
**When to use:** First execution of any code in sandbox requires approval
**Example:**
```typescript
// Based on AI SDK docs and existing toolApproval table schema
// In sandbox-code-tab.tsx

const handleRunCode = async () => {
  const isFirstRun = !hasApprovedOnce;

  if (isFirstRun) {
    // Show inline approval UI within sandbox
    setShowApproval(true);
    return;
  }

  // Auto-execute if previously approved
  executeCode();
};

const handleApprove = () => {
  setHasApprovedOnce(true);
  setShowApproval(false);
  executeCode();

  // Record approval in database (prevent replay attacks)
  addToolApprovalResponse({
    id: toolCallId,
    approved: true,
  });
};

const handleDeny = () => {
  // Close sandbox on denial (per CONTEXT.md decision)
  closeSandbox();

  addToolApprovalResponse({
    id: toolCallId,
    approved: false,
    reason: "User denied code execution",
  });
};
```

### Pattern 3: Database State Persistence
**What:** Store sandbox state in dedicated table for page refresh restoration
**When to use:** Any artifact that needs full state restoration after page reload
**Example:**
```sql

CREATE TABLE "SandboxState" (
  "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "sandboxId" varchar(255) NOT NULL UNIQUE,
  "messageId" uuid NOT NULL REFERENCES "Message_v2"("id") ON DELETE CASCADE,

  "updatedAt" timestamp DEFAULT now()
);
```

```typescript
// In lib/db/queries.ts
export async function saveSandboxState({
  sandboxId,
  messageId,
  chatId,
  title,
  code,
  outputs,
  hasApprovedOnce,
}: SandboxStateInput) {
  return db.insert(sandboxState).values({
    sandboxId,
    messageId,
    chatId,
    title,
    code,
    outputs,
    hasApprovedOnce,
  }).onConflictDoUpdate({
    target: sandboxState.sandboxId,
    set: { code, outputs, hasApprovedOnce, updatedAt: new Date() }
  });
}

export async function getSandboxState(sandboxId: string) {
  return db.query.sandboxState.findFirst({
    where: eq(sandboxState.sandboxId, sandboxId),
  });
}
```

### Pattern 4: Multiple Artifact Management
**What:** Support multiple sandboxes open simultaneously via array state
**When to use:** User opens multiple sandboxes in one conversation
**Example:**
```typescript
// Extend use-artifact.ts pattern for multiple artifacts
export function useSandboxes() {
  const { data: sandboxes, mutate: setSandboxes } = useSWR<UISandbox[]>(
    'sandboxes',
    null,
    { fallbackData: [] }
  );

  const openSandbox = useCallback((sandbox: UISandbox) => {
    setSandboxes(current => [...(current || []), sandbox]);
  }, [setSandboxes]);

  const closeSandbox = useCallback((sandboxId: string) => {
    setSandboxes(current =>
      (current || []).filter(s => s.sandboxId !== sandboxId)
    );
  }, [setSandboxes]);

  const activeSandbox = sandboxes?.[sandboxes.length - 1]; // Most recent

  return { sandboxes, openSandbox, closeSandbox, activeSandbox };
}
```

### Anti-Patterns to Avoid

- **Storing sandbox state in message parts:** Breaks querying, makes restoration complex, violates approval security pattern (Phase 19 established separate toolApproval table)
- **Auto-executing code without approval:** Security risk, violates needsApproval requirement
- **Creating new E2B sandbox per execution:** Expensive, slow, loses environment state (packages installed, files created)
- **Mixing artifact kinds in single component:** CodeArtifact and SandboxArtifact have different lifecycles, keep separate

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Code editor component | Custom textarea with syntax highlighting | CodeMirror 6 (already integrated) | Line numbers, language support, themes, change tracking all built-in |
| Tool approval workflow | Custom approval state management | AI SDK needsApproval + addToolApprovalResponse | Handles two-model-call flow, state sync, type safety automatically |
| ANSI color codes in output | Regex replacement for color codes | ansi-to-react (already in deps) | Handles complex escape sequences, edge cases (cursor positioning, clearing) |
| Visualization thumbnails | Custom image resizing logic | CSS object-fit + click handler | Browser-native, performant, responsive |
| Page refresh state restoration | localStorage manual serialization | SWR + database queries | Handles hydration, race conditions, cache invalidation |
| Tabbed interface | Custom tab state + CSS | Radix UI Tabs | Accessibility (ARIA), keyboard nav, focus management built-in |

**Key insight:** Sandbox artifacts combine multiple complex subsystems (tool calling, code execution, state persistence, approval workflows). Each subsystem has established patterns in the codebase - reuse rather than reinvent.

## Common Pitfalls

### Pitfall 1: Approval State Replay Attacks
**What goes wrong:** User manually modifies message parts to re-submit old approval, bypassing security
**Why it happens:** Storing approval decisions in message parts (client-controlled) instead of server database
**How to avoid:** Phase 19 established pattern - separate toolApproval table with unique constraint on toolCallId, filter approval parts before message persistence
**Warning signs:** Approval responses in saved messages, approval logic trusting client message history

### Pitfall 2: CodeMirror Memory Leaks
**What goes wrong:** Creating new EditorView instances without destroying previous ones causes memory leaks
**Why it happens:** React re-renders create new instances while old ones remain in memory
**How to avoid:** Always call `view.destroy()` in useEffect cleanup, store view in ref, check if view exists before creating new one (pattern in code-editor.tsx lines 37-42)
**Warning signs:** Increasing memory usage when switching between sandboxes, multiple editor DOM nodes for same sandbox

### Pitfall 3: E2B Sandbox Lifecycle Mismanagement
**What goes wrong:** Creating new E2B sandbox for each code execution wastes time (10-15 seconds startup) and money ($0.04-0.20 per sandbox)
**Why it happens:** Treating E2B like stateless function execution instead of persistent environment
**How to avoid:** Store e2bSandboxId in SandboxState table, reuse sandbox across executions until user closes artifact (decision: persistent workspace model)
**Warning signs:** Every execution has 10+ second delay, E2B costs scale with execution count rather than sandbox count

### Pitfall 4: Stale State After Page Refresh
**What goes wrong:** Sandbox appears but code/output missing, or shows old state
**Why it happens:** SWR cache out of sync with database, hydration timing issues
**How to avoid:** Query database on mount, use SWR mutate to update cache, fallback to database if cache empty (pattern in artifact.tsx lines 80-114)
**Warning signs:** Empty sandbox after refresh, console errors about undefined state, flashing content

### Pitfall 5: Output Accumulation Without Clear
**What goes wrong:** Each execution appends to previous output, eventually causing performance issues
**Why it happens:** Forgetting to implement "clear on run" decision from CONTEXT.md
**How to avoid:** Reset outputs array to empty before each execution, timestamp each output entry for debugging
**Warning signs:** Output pane grows unbounded, UI lag when scrolling output, confusion about which output corresponds to which run

### Pitfall 6: Tool Approval Two-Call Flow Misunderstanding
**What goes wrong:** Expecting tool to execute immediately after calling with needsApproval: true
**Why it happens:** AI SDK requires first call to return approval request, second call with approval response to execute
**How to avoid:** First model call generates tool-approval-request parts, store in messages, second call includes tool-approval-response, THEN tool executes (documented in AI SDK core tools guide)
**Warning signs:** Tool execute() never called, approval UI shown but nothing happens after approve, confusion about "why is model generating but not executing"

### Tool Approval Flow (AI SDK Pattern)
```typescript
// Source: https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling
// Pattern: Two model calls with approval in between

// First call - generates approval request
const result1 = await generateText({
  model,
  tools: {
    runCode: tool({
      needsApproval: true,
      execute: async ({ code }) => { /* ... */ }
    })
  },
  messages,
});

// Check for approval requests
messages.push(...result1.response.messages);
const approvalRequests = result1.content.filter(
  part => part.type === 'tool-approval-request'
);

// Collect user approval
const approvals = approvalRequests.map(req => ({
  type: 'tool-approval-response',
  approvalId: req.approvalId,
  approved: true, // or false
  reason: 'User confirmed execution',
}));

messages.push({ role: 'tool', content: approvals });

// Second call - executes tool if approved
const result2 = await generateText({
  model,
  tools: { runCode },
  messages, // Now includes approval response
});
```

```typescript
// Source: docs/components/code-editor.tsx (lines 20-92)
function CodeEditor({ content, onSaveContent, status }: EditorProps) {
  const containerRef = useRef<HTMLDivElement>(null);
  const editorRef = useRef<EditorView | null>(null);

  // Initialize once
  useEffect(() => {
    if (containerRef.current && !editorRef.current) {
      const startState = EditorState.create({
        doc: content,
        extensions: [basicSetup, python(), oneDark],
      });

      editorRef.current = new EditorView({
        state: startState,
        parent: containerRef.current,
      });
    }

    return () => {
      if (editorRef.current) {
        editorRef.current.destroy();
        editorRef.current = null;
      }
    };
  }, []);

  // Update listener for changes
  useEffect(() => {
    if (editorRef.current) {
      const updateListener = EditorView.updateListener.of((update) => {
        if (update.docChanged) {
          const newContent = update.state.doc.toString();
          onSaveContent(newContent, true);
        }
      });

      const newState = EditorState.create({
        doc: editorRef.current.state.doc,
        extensions: [basicSetup, python(), oneDark, updateListener],
      });

      editorRef.current.setState(newState);
    }
  }, [onSaveContent]);

  return <div ref={containerRef} />;
}
```

### E2B Execution with Visualization Upload (Existing Pattern)
```typescript
// Source: docs/lib/mcp/aggregate-tools.ts (lines 54-125)
execute: async ({ code, files, workingDirectory }) => {
  const sandbox = await e2bClient.createSandbox();

  try {
    const result = await sandbox.runCode(code, {
      timeoutMs: 30 * 1000,
      files: files?.map(f => ({ path: f.path, content: f.content })),
      workingDirectory,
    });

    // Upload visualizations to blob storage
    if (result.visualizations && result.visualizations.length > 0) {
      const uploadedViz = await Promise.all(
        result.visualizations.map(async (viz, index) => {
          const urls: { format: string; url: string }[] = [];

          if (viz.png) {
            const url = await uploadImageFromBase64(
              viz.png,
              `viz-${Date.now()}-${index}.png`,
              chatId
            );
            urls.push({ format: 'png', url });
          }

          if (viz.svg) {
            const url = await uploadImageFromBase64(
              viz.svg,
              `viz-${Date.now()}-${index}.svg`,
              chatId
            );
            urls.push({ format: 'svg', url });
          }

          return { formats: viz.formats, urls };
        })
      );

      result.visualizations = uploadedViz;
    }

    return {
      success: true,
      stdout: result.logs.stdout.join('\n'),
      stderr: result.logs.stderr.join('\n'),
      result: result.text,
      visualizations: result.visualizations,
    };
  } finally {
    await sandbox.kill();
  }
}
```

### SWR Artifact State Pattern (Existing)
```typescript
// Source: docs/hooks/use-artifact.ts (lines 39-83)
export function useArtifact() {
  const { data: localArtifact, mutate: setLocalArtifact } = useSWR<UIArtifact>(
    'artifact',
    null,
    { fallbackData: initialArtifactData }
  );

  const artifact = useMemo(() => {
    if (!localArtifact) return initialArtifactData;
    return localArtifact;
  }, [localArtifact]);

  const setArtifact = useCallback(
    (updaterFn: UIArtifact | ((current: UIArtifact) => UIArtifact)) => {
      setLocalArtifact((currentArtifact) => {
        const artifactToUpdate = currentArtifact || initialArtifactData;

        if (typeof updaterFn === 'function') {
          return updaterFn(artifactToUpdate);
        }

        return updaterFn;
      });
    },
    [setLocalArtifact]
  );

  return { artifact, setArtifact };
}
```

## Open Questions

Things that couldn't be fully resolved during research:

1. **Visualization thumbnail sizing**
   - What we know: Decision is thumbnail with click-to-expand, existing artifact.tsx has image rendering patterns
   - What's unclear: Exact pixel dimensions for "reasonable-sized thumbnail", aspect ratio handling for different chart types
   - Recommendation: Start with 400px max-width, maintain aspect ratio, iterate based on user testing

2. **E2B sandbox reuse lifecycle**
   - What we know: Sandbox should persist across executions (decision: persistent workspace), sandbox manager pattern exists
   - What's unclear: When to kill old sandbox (memory/cost constraints), how to detect sandbox is stale/dead
   - Recommendation: Keep sandbox alive for 1 hour of inactivity or until user closes artifact, implement health check ping before reuse

3. **Multiple sandbox interaction model**
   - What we know: Multiple sandboxes can be open simultaneously (decision from CONTEXT.md)
   - What's unclear: UI for switching between sandboxes (tabs? stack? list?), which sandbox is "active" for AI operations
   - Recommendation: Stack/card layout similar to browser tabs, most recent sandbox is active, allow explicit focus change

4. **Output streaming vs batch**
   - What we know: E2B provides onStdout/onStderr callbacks for streaming, existing execute-python collects then returns
   - What's unclear: Should output stream to UI during execution or display all at once after completion
   - Recommendation: Stream for better UX during long executions, matches "Jupyter-style" reference from CONTEXT.md

5. **Syntax highlighting for output**
   - What we know: ansi-to-react handles color codes, output includes stdout/stderr/errors
   - What's unclear: Should errors get syntax highlighting (Python tracebacks), how to distinguish output types visually
   - Recommendation: Use ansi-to-react for raw output, add subtle background colors for error sections, syntax highlight tracebacks
