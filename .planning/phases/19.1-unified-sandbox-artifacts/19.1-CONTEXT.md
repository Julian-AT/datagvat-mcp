# Phase 19.1: Unified Sandbox Artifacts - Context

**Gathered:** 2026-02-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace two separate systems (static document artifacts created via `createDocument` + code execution via `execute-python` tool) with a single unified "sandbox artifact" paradigm. When AI needs to work with code, it opens an interactive sandbox environment that combines code editing, execution approval, output display, and visualization rendering in one artifact (similar to Lovable's approach).

**What's IN scope:**
- Single `openSandbox` tool replacing `createDocument` + `execute-python` for code
- Sandbox artifact UI with code editor, execution controls, and output display
- Integrated approval flow within sandbox
- Persistence of sandbox state across page refresh
- Multiple simultaneous sandboxes in one conversation

**What's OUT of scope:**
- Text and sheet artifacts (remain unchanged - SANDBOX-08)
- Changes to non-code workflows
- Advanced IDE features (debugging, intellisense)

</domain>

<decisions>
## Implementation Decisions

### Sandbox Lifecycle

- **When to open sandbox:** AI always opens sandbox for ANY code-related request (Python, data analysis, charts, algorithms). No need for explicit "run" or "execute" keywords - if it involves code, it's a sandbox.

- **Sandbox persistence:** Sandboxes stay open until user manually closes them (persistent workspace model). No auto-close after execution.

- **Page refresh behavior:** Full state restoration - code, output, execution history, and visualization results all persist and restore when user returns.

- **Multiple sandboxes:** Multiple sandboxes can be open simultaneously in one conversation. User manages them like tabs or cards (implementation details: research common patterns).

### Execution & Approval Flow

- **Approval UI placement:** Inline approval UI within sandbox artifact - approve/deny buttons integrated directly into the sandbox interface (not modal, not separate).

- **Approval frequency:** First run only requires approval. After initial approval, subsequent runs auto-execute without additional approval prompt (even if code changes).

- **Execution trigger:** Explicit 'Run' button for user to click after editing code (Jupyter-style interaction). No auto-execute, no keyboard shortcut requirement (though can be added later).

- **Denial behavior:** When user denies execution, sandbox closes completely and shows "Execution denied" message in chat. No lingering sandbox artifact.

### Output & Visualization Display

- **Layout structure:** Tabbed interface - user switches between 'Code' tab and 'Output' tab (not split-pane, not stacked). Clean separation of editing and results.

- **Output organization:** Single unified output pane showing everything in execution order (console logs, print statements, visualizations, errors all in chronological sequence).

- **Visualization rendering:** Thumbnail with click-to-expand fullscreen. Charts/plots show as reasonable-sized thumbnails inline, user clicks to view fullscreen overlay.

- **Output history:** Clear output on each run - fresh start every execution. No appended history, no execution log accumulation.

### Claude's Discretion

- Exact code editor choice (Monaco, CodeMirror, or other)
- Sandbox UI styling and visual design
- Tab switching animation and transitions
- Thumbnail size for visualizations
- Fullscreen overlay implementation
- Error formatting and display
- Loading states during execution
- Sandbox close button placement and confirmation

</decisions>

<specifics>
## Specific Ideas

- "Like Lovable" - reference product for sandbox artifact UX
- "Jupyter-style" - explicit Run button for execution trigger
- Tabbed interface provides clean separation without split-screen complexity
- First-run-only approval reduces friction for iterative development
- Multiple sandboxes enables comparing different approaches side-by-side
- Clear-on-run keeps output focused on current results, not cluttered with history

</specifics>
