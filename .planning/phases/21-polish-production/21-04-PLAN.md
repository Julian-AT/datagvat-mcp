# Plan 21-04: Fix Race Conditions & Optimize Execution Flow

**Issue:** The console logs show `Foreign key violation (likely message not persisted yet)` when `saveSandboxState` is called. This indicates that `SandboxArtifact` is trying to save the sandbox state *before* the chat message (which contains the sandbox ID) is fully persisted in the database.

**Root Cause:**
1.  Frontend: `SandboxArtifact` component mounts and immediately triggers `saveToDb`.
2.  Backend: `POST /api/chat` (streaming response) is still running.
3.  The message ID exists on the client (optimistically), but the `Message` row hasn't been committed to Postgres yet.
4.  `POST /api/sandbox` fails with FK violation (as seen in logs).
5.  Retry logic works (eventually), but it causes 422 errors and delays.

**Secondary Issue:**
Execution flow seems slow (35s for chat response, 8s for execution).

**Goal:**
1.  Eliminate the race condition by ensuring `saveSandboxState` only runs *after* the message is likely persisted, or improve the retry logic to be silent/faster.
2.  Optimize the "Auto Run" behavior to avoid redundant executions.

**Files to Modify:**
1.  `docs/components/sandbox-artifact.tsx`
    *   Delay the initial `saveToDb` slightly or rely on the `useEffect` dependency change more intelligently.
    *   The current retry logic `setTimeout(() => saveToDb(attempt + 1), delay)` is correct but verbose in logs.
    *   We can also try to "upsert" the message if it doesn't exist (complex) OR just wait.
    *   **Better approach:** The `SandboxArtifact` is rendered *by* the message. If the message is streaming, the DB row might not exist.
    *   **Fix:** In `SandboxArtifact`, if `messageId` is optimistic (generated client-side or streaming), we should wait for a confirmation or just accept the retry loop but silence the error for the first few seconds.

**Plan Steps:**
